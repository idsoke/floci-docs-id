🔑 Modul 6 · IAM: Siapa Boleh Apa

⏱ 90 menit📶 Menengah🧩 AWS IAM + STS
Penjelasan sederhana

IAM adalah satpam dan sistem kartu akses gedung. Setiap orang (user) atau mesin (role) membawa kartu. Kartu itu terhubung ke daftar aturan (policy) seperti "boleh masuk lantai 3, tidak boleh masuk ruang server". Setiap kali ada request, satpam mengecek aturan.

Aturan dasarnya: semua dilarang kecuali diizinkan, dan larangan eksplisit selalu menang atas izin.

Tujuan modul

  • Menyalakan mode penegakan IAM di Floci, karena default-nya Floci mengizinkan semua request.
  • Membuat user dan access key, lalu melihat sendiri request ditolak (AccessDenied).
  • Membaca dan menulis policy JSON: Effect, Action, Resource.
  • Memahami urutan evaluasi: default deny → allow → explicit deny.
  • Memakai role dan kredensial sementara lewat sts assume-role.

Konsep kunci

IstilahArti
RootPemilik akun, boleh segalanya. Di AWS asli jangan dipakai sehari-hari. Di Floci, kredensial test = root.
UserIdentitas permanen untuk orang atau aplikasi, punya access key jangka panjang
RoleIdentitas yang "dipakai sementara" oleh user, layanan (mis. Lambda), atau akun lain. Kredensialnya kedaluwarsa.
PolicyDokumen JSON berisi statement: Effect (Allow/Deny), Action (mis. s3:GetObject), Resource (ARN)

Langkah praktik

Nyalakan Floci dengan penegakan IAM

Secara default Floci tidak mengecek policy agar mudah dipakai. Untuk modul ini kita aktifkan pengecekan. (Restart ini menghapus data latihan sebelumnya.)

docker rm -f floci
docker run -d --name floci -p 4566:4566 \
  -v /var/run/docker.sock:/var/run/docker.sock -u root \
  -e FLOCI_SERVICES_IAM_ENFORCEMENT_ENABLED=true \
  floci/floci:latest

sleep 3; docker logs floci 2>&1 | grep "IAM:"
… IAM:       policy enforcement enabled

Kredensial test tetap bebas (dianggap root). Pembatasan berlaku untuk user dan role yang kita buat.

Buat data uji, user "magang", dan access key-nya

# sebagai root (kredensial test)
aws s3 mb s3://laporan
echo "omzet naik 10%" > ringkas.txt; aws s3 cp ringkas.txt s3://laporan/umum/ringkas.txt
echo "gaji direksi"   > gaji.txt;    aws s3 cp gaji.txt    s3://laporan/rahasia/gaji.txt

aws iam create-user --user-name magang --query User.Arn
read MAGANG_AK MAGANG_SK <<< $(aws iam create-access-key --user-name magang \
  --query 'AccessKey.[AccessKeyId,SecretAccessKey]' --output text)
echo $MAGANG_AK

# fungsi bantu: jalankan perintah aws sebagai magang
sebagai_magang() { AWS_ACCESS_KEY_ID=$MAGANG_AK AWS_SECRET_ACCESS_KEY=$MAGANG_SK aws "$@"; }
sebagai_magang sts get-caller-identity --query Arn
"arn:aws:iam::000000000000:user/magang"
AKIA…
"arn:aws:iam::000000000000:user/magang"

Fungsi sebagai_magang hanya mengganti kredensial untuk satu perintah. Terminal Anda tetap memakai test. sts get-caller-identity selalu diizinkan, bahkan tanpa policy.

Lihat request ditolak

sebagai_magang s3 ls
sebagai_magang sqs list-queues
An error occurred (AccessDenied) when calling the ListBuckets operation: …
An error occurred (AccessDeniedException) when calling the ListQueues operation: …

User baru tidak punya izin apa pun (implicit deny). Kode error-nya berbeda per protokol: S3 memakai AccessDenied (HTTP 403), sedangkan layanan JSON seperti SQS memakai AccessDeniedException (HTTP 400). Keduanya sama artinya: tidak boleh.

Beri izin baca dengan policy

cat > baca-laporan.json <<'EOF'
{
  "Version": "2012-10-17",
  "Statement": [
    { "Sid": "LihatDaftarBucket", "Effect": "Allow",
      "Action": "s3:ListAllMyBuckets", "Resource": "*" },
    { "Sid": "LihatIsiBucketLaporan", "Effect": "Allow",
      "Action": "s3:ListBucket", "Resource": "arn:aws:s3:::laporan" },
    { "Sid": "BacaFileLaporan", "Effect": "Allow",
      "Action": "s3:GetObject", "Resource": "arn:aws:s3:::laporan/*" }
  ]
}
EOF
aws iam put-user-policy --user-name magang --policy-name baca-laporan \
  --policy-document file://baca-laporan.json

sebagai_magang s3 ls
sebagai_magang s3 cp s3://laporan/umum/ringkas.txt -
sebagai_magang s3 cp ringkas.txt s3://laporan/umum/coba-tulis.txt
2026-11-01 10:00:00 laporan
omzet naik 10%
upload failed: ./ringkas.txt to s3://laporan/umum/coba-tulis.txt An error occurred (AccessDenied) when calling the PutObject operation: …

Membaca boleh, menulis tidak, karena kita tidak memberi s3:PutObject. Perhatikan dua bentuk Resource: arn:aws:s3:::laporan = bucket-nya (untuk list), arn:aws:s3:::laporan/* = object di dalamnya.

Larangan eksplisit (Deny) selalu menang

cat > larang-rahasia.json <<'EOF'
{
  "Version": "2012-10-17",
  "Statement": [
    { "Effect": "Deny", "Action": "s3:*", "Resource": "arn:aws:s3:::laporan/rahasia/*" }
  ]
}
EOF
aws iam put-user-policy --user-name magang --policy-name larang-rahasia \
  --policy-document file://larang-rahasia.json

sebagai_magang s3 cp s3://laporan/umum/ringkas.txt -
sebagai_magang s3 cp s3://laporan/rahasia/gaji.txt -
aws iam list-user-policies --user-name magang
omzet naik 10%
fatal error: An error occurred (403) when calling the HeadObject operation: Forbidden
{
    "PolicyNames": [
        "baca-laporan",
        "larang-rahasia"
    ]
}

Untuk download, CLI memanggil HeadObject lebih dulu. Respons HEAD tidak punya body, jadi yang tampil hanya 403 Forbidden, bukan kode AccessDenied. Artinya tetap sama.

baca-laporan mengizinkan laporan/*, tetapi larang-rahasia melarang laporan/rahasia/*. Karena Deny menang, file rahasia tetap tertutup.

Role dan kredensial sementara

Skenario: magang sesekali perlu mengelola antrean SQS. Daripada menambah izin permanen, kita buat role pengelola-antrean yang boleh "dipinjam" oleh magang.

# 1) Trust policy: SIAPA boleh memakai role ini
cat > trust.json <<'EOF'
{ "Version": "2012-10-17",
  "Statement": [{ "Effect": "Allow", "Action": "sts:AssumeRole",
                  "Principal": { "AWS": "arn:aws:iam::000000000000:user/magang" } }] }
EOF
ROLE_ARN=$(aws iam create-role --role-name pengelola-antrean \
  --assume-role-policy-document file://trust.json --query Role.Arn --output text)

# 2) Izin role: APA yang boleh dilakukan role ini
aws iam put-role-policy --role-name pengelola-antrean --policy-name sqs-penuh \
  --policy-document '{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Action":"sqs:*","Resource":"*"}]}'

# 3) Magang juga harus diizinkan memanggil sts:AssumeRole ke role itu
aws iam put-user-policy --user-name magang --policy-name boleh-pinjam-role \
  --policy-document "{\"Version\":\"2012-10-17\",\"Statement\":[{\"Effect\":\"Allow\",\"Action\":\"sts:AssumeRole\",\"Resource\":\"$ROLE_ARN\"}]}"

# 4) Magang meminjam role → dapat kredensial sementara
read RAK RSK RTOK <<< $(sebagai_magang sts assume-role --role-arn $ROLE_ARN \
  --role-session-name sesi-magang \
  --query 'Credentials.[AccessKeyId,SecretAccessKey,SessionToken]' --output text)

AWS_ACCESS_KEY_ID=$RAK AWS_SECRET_ACCESS_KEY=$RSK AWS_SESSION_TOKEN=$RTOK aws sts get-caller-identity --query Arn
AWS_ACCESS_KEY_ID=$RAK AWS_SECRET_ACCESS_KEY=$RSK AWS_SESSION_TOKEN=$RTOK aws sqs create-queue --queue-name antrean-magang
AWS_ACCESS_KEY_ID=$RAK AWS_SECRET_ACCESS_KEY=$RSK AWS_SESSION_TOKEN=$RTOK aws s3 ls
import os, boto3

magang = boto3.Session(aws_access_key_id=os.environ["MAGANG_AK"],
                       aws_secret_access_key=os.environ["MAGANG_SK"])
cred = magang.client("sts").assume_role(
    RoleArn="arn:aws:iam::000000000000:role/pengelola-antrean",
    RoleSessionName="sesi-python")["Credentials"]

sesi_role = boto3.Session(aws_access_key_id=cred["AccessKeyId"],
                          aws_secret_access_key=cred["SecretAccessKey"],
                          aws_session_token=cred["SessionToken"])
print(sesi_role.client("sts").get_caller_identity()["Arn"])
print(sesi_role.client("sqs").list_queues().get("QueueUrls"))
print("berlaku sampai", cred["Expiration"])

# jalankan dengan: export MAGANG_AK MAGANG_SK; python role.py
"arn:aws:sts::000000000000:assumed-role/pengelola-antrean/sesi-magang"
{ "QueueUrl": "http://localhost:4566/000000000000/antrean-magang" }
An error occurred (AccessDenied) when calling the ListBuckets operation: …

Saat memakai role, izin magang sendiri tidak terbawa: sesi role hanya boleh SQS, sehingga s3 ls ditolak. Access key sementara diawali ASIA dan wajib disertai SessionToken.

Begitu juga cara Lambda bekerja: fungsi berjalan dengan kredensial sementara dari execution role-nya.

Kembali ke mode normal

Untuk Modul 7, jalankan lagi Floci tanpa penegakan IAM agar fokus pada alur aplikasi:

docker rm -f floci
docker run -d --name floci -p 4566:4566 \
  -v /var/run/docker.sock:/var/run/docker.sock -u root \
  floci/floci:latest

Di dunia nyata justru sebaliknya: selalu biasakan menguji aplikasi dengan penegakan IAM sebelum deploy, agar kekurangan izin ketahuan di laptop dan bukan di produksi.

Anatomi sebuah policy

{
  "Version": "2012-10-17",                  ← selalu tulis persis begini
  "Statement": [{
    "Sid": "BacaFileLaporan",                ← nama bebas (opsional)
    "Effect": "Allow",                       ← Allow atau Deny
    "Action": ["s3:GetObject"],              ← layanan:Operasi, boleh pakai * (s3:Get*)
    "Resource": "arn:aws:s3:::laporan/*",    ← resource yang dikenai
    "Condition": {                           ← opsional: syarat tambahan
      "IpAddress": { "aws:SourceIp": "10.0.0.0/8" }
    }
  }]
}

Latihan mandiri

Latihan 1. Beri magang izin menulis hanya ke prefix laporan/draft/. Buktikan bisa menulis ke draft/ tetapi tidak ke umum/.
Lihat kunci jawaban 
aws iam put-user-policy --user-name magang --policy-name tulis-draft --policy-document \
 '{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Action":"s3:PutObject","Resource":"arn:aws:s3:::laporan/draft/*"}]}'
sebagai_magang s3 cp ringkas.txt s3://laporan/draft/a.txt     # berhasil
sebagai_magang s3 cp ringkas.txt s3://laporan/umum/a.txt      # AccessDenied
Latihan 2. Nonaktifkan access key magang, lalu coba sebagai_magang s3 ls. Error apa yang muncul?
Lihat kunci jawaban 
aws iam update-access-key --user-name magang --access-key-id $MAGANG_AK --status Inactive
sebagai_magang s3 ls

Request ditolak karena kunci tidak aktif lagi. Inilah langkah pertama jika sebuah access key bocor: nonaktifkan, buat yang baru, lalu hapus yang lama.

Kuis

1. Policy A mengizinkan s3:* pada semua resource. Policy B melarang s3:DeleteObject. Bolehkah user menghapus object?
Urutan pembuatan tidak berpengaruh. Satu Deny yang cocok sudah cukup untuk menolak.
2. User baru tanpa policy apa pun mencoba dynamodb list-tables. Hasilnya?
Default IAM adalah menolak. Izin harus diberikan secara eksplisit.
3. Cara terbaik memberi fungsi Lambda akses ke DynamoDB?
Role memberi kredensial sementara yang berganti otomatis, dan least privilege membatasi kerusakan jika ada bug atau kebocoran.

Di AWS asli, apa bedanya?

  • IAM selalu aktif. Tidak ada mode "izinkan semua" seperti default Floci.
  • Segera aktifkan MFA untuk root, lalu buat user/Identity Center untuk kerja sehari-hari.
  • Gunakan AWS managed policy (mis. ReadOnlyAccess) sebagai titik awal, dan IAM Access Analyzer untuk mengecek izin berlebih.
  • Jangan pernah commit access key ke Git.
