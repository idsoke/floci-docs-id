Penyimpanan Data (Storage)

Semua state layanan (antrean, tabel, bucket, fungsi, parameter) disimpan lewat satu abstraksi: StorageBackend. Ada empat mode yang bisa dipilih global atau per layanan.

Penjelasan sederhana

Bayangkan Anda mencatat di papan tulis (memori, cepat tapi hilang kalau dihapus) dan buku arsip (disk, awet tapi lebih lambat ditulis).

🧽 memory: hanya papan tulis. Restart = bersih total.
📒 persistent: setiap kali papan berubah, langsung disalin ke buku. Aman, tapi menyalin terus.
⏱️ hybrid: tulis di papan dulu, lalu salin ke buku tiap beberapa detik. Cepat, tapi perubahan terakhir bisa hilang kalau listrik mati.
🧾 wal: setiap perubahan dicatat sebagai satu baris pendek di buku jurnal, sesekali jurnal dirangkum jadi salinan lengkap. Cepat dan awet.

Format entri WAL biner

PUT:          [0x01] [4-byte panjang key] [key] [4-byte panjang value] [value]
DELETE:       [0x02] [4-byte panjang key] [key]
BATCH:        [0x03] [4-byte panjang map] [map CBOR]
DELETE_BATCH: [0x04] [4-byte panjang array] [array key CBOR]

Key dan value diserialisasi dengan Jackson CBOR (biner ringkas). File snapshot memakai JSON berindentasi supaya mudah diperiksa manusia. Kompaksi dilewati bila tidak ada perubahan sejak snapshot terakhir. Interval default: FLOCI_STORAGE_WAL_COMPACTION_INTERVAL_MS=30000.

Isolasi per akun

Setiap storage yang dibuat StorageFactory dibungkus AccountAwareStorageBackend. Pembungkus ini menambahkan prefix akun ke setiap key secara transparan:

Akun 111111111111 membuat antrean "orders"  →  key: 111111111111/orders
Akun 222222222222 membuat antrean "orders"  →  key: 222222222222/orders   (terpisah total)
  • Di jalur request, account ID dibaca dari RequestContext yang diisi AccountContextFilter.
  • Di luar request (worker async, startup) dipakai default account. Worker yang perlu akun tertentu memakai overload *ForAccount dengan account ID yang tersimpan di model resource.
  • Kompatibilitas mundur: bila key ber-prefix tidak ditemukan, key lama tanpa prefix dicoba lalu dimigrasikan saat dibaca.

Fitur storage lanjutan

📓 Journaled stores (mode persistent)

Store yang sering di-append, yaitu event CloudWatch Logs (cwlogs-events.json + .wal), datapoint metrik CloudWatch, dan indeks objek S3, memakai jurnal. File JSON hanya ditulis ulang tiap interval kompaksi dan saat shutdown.

🧩 PartitionedFileStorage

Untuk store yang nilainya berupa map (mis. item DynamoDB per tabel). Satu file per shard, sehingga mengubah tabel kecil tidak menulis ulang tabel besar. Diatur dengan FLOCI_STORAGE_SERVICES_DYNAMODB_ITEM_LAYOUT=per-table dan ..._ITEM_SHARDS.

⚛️ putAllAtomically

Operasi opsional untuk mengganti beberapa record terkait sekaligus. Persistent menulis snapshot kandidat lengkap dulu; WAL menulis satu frame batch sehingga replay menerapkan semua atau tidak sama sekali.

🚑 Karantina file rusak

StorageQuarantine memindahkan file JSON yang gagal dibaca ke .corrupt, agar kehilangan data terlihat jelas, tidak diam-diam mulai kosong.

# docker-compose.yml: data bertahan antar restart
services:
  floci:
    image: floci/floci:latest
    ports: ["4566:4566"]
    environment:
      FLOCI_STORAGE_MODE: hybrid
      FLOCI_STORAGE_SERVICES_DYNAMODB_MODE: wal
    volumes:
      - ./floci-data:/app/data

Aturan untuk kontributor

  1. Selalu ambil storage dari StorageFactory. Jangan membuat InMemoryStorage dkk. langsung di service.
  2. Hormati hook lifecycle: loadAll() saat start, flushAll()/shutdownAll() saat berhenti.
  3. Implementasikan Resettable agar layanan bisa dikosongkan.
  4. Konfigurasi baru: EmulatorConfig → application.yml utama → application.yml tes → wiring di StorageFactory → cek lifecycle.
